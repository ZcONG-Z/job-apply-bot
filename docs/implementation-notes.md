# Phase 0 实现说明

记录 `profile build` 这条链路的实现细节与设计取舍。架构全貌见 [design.md](design.md)，字段定义见 [profile-schema.md](profile-schema.md)。

---

## 数据流

```
简历文件 (PDF/DOCX)
   │  extract.py      → 按行序抽取纯文本
   ▼
纯文本
   │  parse.py        → 按小节切块，正则 + 版面启发式提取
   ▼
Profile 草稿 + warnings
   │  schema.py       → pydantic 校验（格式、区间、枚举）
   ▼
profile.json
   │  review 命令     → 零容忍字段逐项人工确认
   ▼
可用的事实源
```

四层各管一件事，不互相越界：

| 模块 | 只负责 | 明确不做 |
|---|---|---|
| `extract.py` | 文件 → 保留行序的文本 | 不做结构识别 |
| `parse.py` | 文本 → 字段草稿 | 不做格式校验、不改数据 |
| `normalize.py` | 格式归一（日期、绩点、手机号） | 不做判断，只做转换 |
| `schema.py` | 结构校验 | 不猜测缺失值 |

## 为什么规则优先，而不是直接上大模型

这是本项目最重要的一个取舍。

**规则优先的理由：**

1. **可解释**。抽错了能定位到具体哪条正则、哪一行。大模型说"我判断这是专业"，你没法追问依据。
2. **可测试**。正则可以写单元测试，128 个用例覆盖各种写法。大模型的输出不稳定，测试只能做模糊断言。
3. **零成本、零延迟、零隐私风险**。简历文本包含身份证和住址，发给第三方模型是额外风险面。
4. **规整排版占多数**。中国简历的排版范式很固定，"时间 学校 专业 学历"这一行几乎家家如此。

**大模型的位置**：兜底。规则失败的段落才交给模型，且必须显式开启（`--llm`），因为那意味着简历文本会离开本机。这个设计在 `docs/design.md` 的 Phase 0 里有记录。

## 解析策略：靠位置，还是靠标签

中国简历有两种写法：

```
专业：计算机科学与技术          ← 有标签，正则直接命中
2023.09 - 2027.06  某某大学  计算机科学与技术  本科   ← 无标签，靠位置推断
```

第二种更常见。所以 `parse.py` 里每类字段都有两条路径：先找标签，找不到再按词序推断。

`_major_from_layout()` 的规则是：在学校那一行里，取学校后面第一个**不是**学历、不是日期、不含数字的词元。这个规则不优雅，但覆盖了绝大多数排版。

代价是可能误判——比如排版成"某某大学 上海 计算机科学与技术"，会把"上海"当成专业。这类错误靠 `review` 环节兜底，不靠把正则写得更复杂。**宁可承认局限，也不要堆一条谁也看不懂的正则。**

## 为什么归一化要单独一层

统计下来，填错字段的原因里，格式问题远多于识别问题：

| 现象 | 根因 |
|---|---|
| 网申系统把 2023-09 存成了 2023-9 校验失败 | 月份没补零 |
| 绩点 3.62 被填成 3.6 | 系统只收一位小数，没做适配 |
| 手机号带空格被拒 | 没清洗分隔符 |
| 中文逗号被转成半角，简历正文读起来别扭 | 用了 `NFKC` 做全角转换 |

最后一条是真踩过的坑。最初 `clean()` 用 `unicodedata.normalize("NFKC", ...)`，它会把全角字符全部折叠，包括中文逗号「，」→「,」。结果抽出来的经历描述变成"负责订单服务重构,将核心接口……"，写回 profile 后是脏数据。

改成只转换影响正则匹配的字符（全角数字、`．／－％＠`、全角空格），中文标点原样保留。`tests/test_normalize.py::TestTextHelpers::test_clean_keeps_chinese_punctuation` 锁住了这个行为。

## 零容忍字段

有四类字段填错的代价远高于其他：**出生日期、身份证号、手机号、教育起止时间**。

它们的处理和其他字段不同：

1. schema 里做严格校验（身份证 18 位、手机 `1[3-9]\d{9}`、月份 `YYYY-MM`、起止先后、绩点不超满分制）
2. `build` 的输出表里标注"零容忍"来源
3. `review` 命令强制逐项列出，不允许一键确认
4. 抽不到就留空并写入 warnings，**绝不猜**

第 4 条有个具体例子：简历只写了出生年月没写日。猜"1 号"看起来无害，但网申系统的生日字段往往和身份核验挂钩，填错会被判定信息不一致。所以代码里填了 1 号，但同时在 warnings 里明确说"日期只精确到月，日暂填 1，请核对"——**猜也要让人知道猜了**。

## 实测中修掉的问题

第一版跑通后，用样本简历实测，暴露了四个问题。记录在这里，因为它们都是"只看代码看不出来"的：

| 问题 | 根因 | 修法 |
|---|---|---|
| 公司名抽成"某某科技" | 后缀候选里有"科技"，懒惰匹配提前收尾 | 改成贪婪匹配 + 后缀按长度排序，去掉"科技" |
| 专业、职位抽不到 | 只实现了标签匹配 | 补位置推断（`_major_from_layout` / `_title_from_layout`） |
| 求职意向丢失 | 表头字段漏了解析 | 加 `_INTENT` 正则 |
| 主修课程为空 | 只解析了绩点和排名 | 补课程行识别 |

另外两个是**单元测试抓出来的**：

| 问题 | 根因 |
|---|---|
| `【教育背景】` 标题识别失败 | 标题装饰字符只在正则里处理了前缀括号 |
| 身份证小写 `x` 没转大写 | 脱敏字符集里误放了 `x/X`，末位校验码被当成脱敏值直接跳过了校验 |

第二个 bug 值得多说一句：`MASK_CHARS = ("*", "x", "X")` 的意图是"含 * 的值是脱敏值，跳过校验"。但身份证末位校验码本身就可能是 X，这个"宽容"反而让大小写规范化失效了。**过度的容错也是一种 bug。**

## 测试策略

```
tests/
├── test_smoke.py      # 仓库层面：CLI 可用、示例数据合法、.gitignore 安全规则没被删
├── test_normalize.py  # 归一化：45 个用例覆盖真实世界的各种写法
├── test_schema.py     # 校验：该拦的拦住，该放的放行
└── test_parse.py      # 解析：纯文本 + 端到端跑真实文件
```

几条原则：

- **用例就是样本**。`to_month` 的每个 case 都对应简历里真实出现过的写法。
- **端到端跑真文件**，不只测纯文本。`extract` 和 `parse` 之间的问题只有串起来才看得见。
- **测"该失败"的情况**。手机号 10 位、绩点超过满分、开始晚于结束，都要断言抛错。
- **安全规则也要测**。`test_gitignore_protects_personal_data` 会检查 `.gitignore` 里那 7 条敏感路径规则还在不在——防止有人顺手删掉。

当前 128 个用例，CI 覆盖 Python 3.11 / 3.12 / 3.13 与 Windows。

## 已知局限

诚实列出来，这些不是"以后优化"，是当前客观做不到的：

1. **双栏简历会错**。按阅读框抽取会打乱顺序，导致学校和专业错位。
2. **扫描件不支持**。没有 OCR，纯图片 PDF 抽不出文字（会明确报错，不会静默产出空结果）。
3. **英文简历不支持**。小节关键词只有中文。
4. **多段教育经历的时间线交叉**时，按"含时间区间的行"切块可能切错。
5. **不做事实校验**。它能看出"绩点超过满分"，看不出"绩点是不是你的"。

第 5 条是设计边界：工具负责搬运，不负责判断真实性。
